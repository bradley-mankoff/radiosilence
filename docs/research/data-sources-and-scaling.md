# Data sources and scaling: win probability for every team

Date: 2026-10-25. Codebase: Bad Game Warning (`app.py` in `/Users/bradley_mankoff/Developer/personal_code/bad_game_warning`), a spoiler-free page that reads ESPN's unofficial public site API (`site.api.espn.com`) and sends the phone only a verdict, never a score, clock, or percentage. Question: how to scale from one Dallas Mavericks page to all teams, possibly other leagues, with per-team criteria.

## Answer

ESPN's unofficial `site.api.espn.com` exposes a `winprobability` array in the game summary endpoint for the NBA, WNBA, NFL, college football, MLB, and men's college basketball, but not for the NHL or soccer (MLS and Premier League return no such key). ESPN's governing terms (the Disney Terms of Use, which cover ESPN products) allow only personal, noncommercial use and explicitly forbid automated extraction, scraping, and redistribution, so any scaled or commercial deployment needs a licensed feed. Among licensed alternatives, only balldontlie publishes prices (Free $0/month to All-Access $299.99/month) and it offers no win probability; SportsDataIO, Sportradar, Stats Perform/Opta, and Genius Sports are enterprise sales-led feeds whose win-probability endpoints must be confirmed with sales, while `nba_api` is a free MIT-licensed scraper of stats.nba.com with no service guarantee. The official NBA stats backend actually has a dedicated `winprobabilitypbp` endpoint that is richer than ESPN's (per-event home and visitor percentages plus period and seconds remaining), but it is equally unofficial and is bot-gated. The efficient all-teams design polls one league scoreboard plus one summary per live game (about 16 requests per cycle, roughly 5,800 requests per heavy night at a 30-second cadence), never per-team schedules, because one team schedule payload is about 843KB for the whole season while one scoreboard covers the night in about 200KB.

## 1. Which ESPN leagues expose winprobability

Method: for each league, `GET /apis/site/v2/sports/{sport}/{league}/scoreboard` (optionally with `?dates=YYYYMMDD` for an off-day league), pick a finished (`post`) event id, then `GET .../summary?event=ID` and inspect the top-level `winprobability` key. Join notes (these matter for porting `app.py`'s verdict logic, which joins readings to plays on `playId`):

* NBA, WNBA, and men's college basketball summaries include a `plays` array whose entries carry `id`, `period.number`, and `clock.displayValue`. The tested NBA summary had 486 plays for 486 readings, a one-to-one join. The current app's approach ports directly.
* NFL and college football summaries have NO `plays` array. They expose `drives` and `scoringPlays` instead (the tested NFL summary's top-level keys were `againstTheSpread, article, boxscore, broadcasts, drives, format, gameInfo, header, injuries, leaders, meta, news, odds, pickcenter, scoringPlays, standings, videos, wallclockAvailable, winprobability`). A football verdict rule needs its own clock source, since `clock.displayValue` lives on `scoringPlays` entries, and the exact `playId` join target was not verified in this pass.
* MLB summaries include both `plays` (633 entries) and `winprobability` (78 entries), so the join is many-to-one, and MLB plays carry an inning in `period` (`Top/Bottom`, `number`, `displayValue` like `9th Inning`) but no game clock. A baseball rule must be inning-based, not clock-based.
* NHL summaries include a `plays` array (261 entries in the tested game) with `period` and `clock`, so the plumbing for a hockey rule exists, but there is no win-probability feed to drive it. The same gap a fan project would have to fill with a model or a licensed feed.
* Soccer summaries have neither `winprobability` nor `plays`. They expose `commentary` and `keyEvents`. No win-probability scaling path on ESPN for soccer.

## 2. ESPN terms of use

There is no public developer program, API documentation, or terms page for `site.api.espn.com` itself. The endpoint is undocumented (its responses carry only a `link: <scoreboard.json#>; rel="describedby"` header), which matches the history that ESPN retired its public developer API years ago and this host is ESPN's own front-end data feed, not a licensed product. Use of ESPN content is governed by the Disney Terms of Use (ESPN is a Disney product; the ESPN site footer links to Terms of Use, and the canonical text lives at `https://disneytermsofuse.com/english/`, verified via the site's WordPress API as page id 878 on 2026-10-25). The operative passages state:

* License scope: "we grant you a limited, non-exclusive, non-sublicensable, non-transferable license to access and use in the United States such software, content, virtual item or other material for your personal, noncommercial use only ... with no right to reproduce, distribute, communicate to the public, make available to the public, or transform any Disney Product" (disneytermsofuse.com/english/).
* Automation ban: users may not "access, monitor, copy or extract the Disney Products using a robot, spider, script, or other automated means, including, for the avoidance of doubt, ... data mining or web scraping or otherwise compiling, building, creating or contributing to any collection of data, data set or database (other than for a public search engine's use of spiders for creating search indices...)" (same source). A server that polls ESPN on a schedule is plainly a script extracting content on automated means.
* Remedy for breach: "Any attempt to perform any of the restricted actions listed above is a violation of the rights of Disney and/or the intellectual property rights holder" (same source).

Practical reading: the current single-team personal page sits in the same gray area as every other ESPN-scraping side project, and that risk is the owner's to judge. Scaling to a multi-team service, let alone anything commercial or redistributed, falls outside what the terms permit, so a licensed feed (section 3) becomes a requirement rather than an option.

Rate limits and blocking: ESPN documents no rate limit for this host, and its responses carry no rate-limit headers (observed headers on 2026-10-25: `access-control-allow-origin: *`, `cache-control: max-age=3` on the scoreboard and `max-age=6` on summaries, i.e. content refreshes every few seconds). A 20-request rapid burst from one residential IP on 2026-10-25 returned 20 consecutive HTTP 200 responses with no 429 and no CAPTCHA. That shows modest polling is tolerated, but the blocking threshold is unpublished and remains unknown (see section 6). Community reports of IP blocks under sustained aggressive polling exist but were not verified in this pass.

## 4. Official NBA stats endpoints vs ESPN

stats.nba.com exposes a dedicated endpoint, `winprobabilitypbp`, confirmed via the `nba_api` client source (`src/nba_api/stats/endpoints/winprobabilitypbp.py` in `swar/nba_api`, fetched from `raw.githubusercontent.com` on 2026-10-25). It takes `GameID` and `RunType` and returns two datasets: `GameInfo` (game id, date, teams, score) and `WinProbPBP` with one row per event carrying `GAME_ID, EVENT_NUM, HOME_PCT, VISITOR_PCT, HOME_PTS, VISITOR_PTS, HOME_SCORE_MARGIN, PERIOD, SECONDS_REMAINING, HOME_POSS_IND, DESCRIPTION, LOCATION, PCTIMESTRING, ISVISIBLE`. Compared with ESPN's three fields (`homeWinPercentage, tiePercentage, playId`), the official endpoint is strictly richer for this app's purpose: it reports both sides' percentages directly and, critically, reports `SECONDS_REMAINING` as a number, which would eliminate `app.py`'s clock-string parsing (`seconds_left`, which handles ESPN's `6:00` versus `45.2` display formats).

The catches, all verified by direct probing on 2026-10-25:

* stats.nba.com is unreachable by script from this network: a fully-headered request (browser user agent plus `Referer`, `Origin`, `x-nba-stats-origin`, `x-nba-stats-token`) to `stats/winprobabilitypbp?GameID=0022600045` timed out with no HTTP response after 30 seconds.
* `cdn.nba.com` (the `liveData` host that serves the live play-by-play JSON `nba_api` can also consume) answers curl with HTTP 403 "Access Denied" from its bot manager, with both the schedule and scoreboard paths tested.
* `nba_api` works around this gating with browser-like headers from ordinary environments, but that is the same unofficial scraping posture as the ESPN feed: no terms permit it, headers and gating change without notice, and there is no uptime guarantee.

So the official NBA backend has the better win-probability data model, but it is harder to reach by script than ESPN's feed and carries the same licensing problem. Nothing about it recommends migrating the current app; it is worth knowing only as the fallback if ESPN ever removes `winprobability` from summaries, and as the thing to license properly through Genius Sports or Sportradar if the project goes commercial.

## 5. Serving all 30 NBA teams efficiently

The current app does 2 ESPN requests per page view (one team schedule plus one summary) and refreshes every 60 seconds, so one always-open phone costs about 2,880 requests per day. That design scales with viewers times teams and must be replaced by a single server-side poller whose cost is independent of viewer count. Two poller shapes were compared using measured payload sizes from 2026-10-25 (NBA scoreboard with 8 games: 201,614 bytes; one NBA summary: 475,921 bytes; one NFL summary: 556,066 bytes; one Mavericks team schedule: 843,192 bytes):

* Per-game polling (recommended): one league scoreboard per cycle to discover which games are live, plus one summary per live game. Cost per cycle is 1 + G requests where G is live games. At a 30-second cadence (matching ESPN's own `max-age=6` freshness (120 cycles per hour times a 3-hour evening window): with 15 concurrent games, 16 requests times 360 cycles is about 5,760 requests per night; with a typical 8 live games it is about 3,240. Bandwidth is the real budget: roughly 200KB plus G times 500KB per cycle, or about 7.7MB per cycle at G=15, near 0.9GB over a heavy night. Halving cadence to 60 seconds halves both numbers and is still fine for a stay-away verdict that flips on 6-minute boundaries. This shape also ports to every league in section 1 with a `winprobability` array, since the scoreboard-then-summary pattern is identical and only the verdict rule changes per sport.
* Per-team polling (rejected): one team-schedule fetch per team per cycle, 30 requests per cycle before any summary, moving about 30 times 843KB or 25MB per cycle. The team schedule returns the entire season to answer "is there a game tonight," which the one-day scoreboard already answers for all teams in 200KB. It costs roughly 30 times the requests and 3 times the bandwidth for strictly less information, then still needs the same per-game summaries. There is no case where per-team polling wins.

Two refinements worth adding when building the poller: skip summary fetches for games whose scoreboard state is `pre` or `post` (only `in` games can flip the verdict, plus one final fetch at `post` for the completed-game display the owner already decided on), and slow polling for games outside the verdict window (first half before the 6-minutes-left-in-Q2 threshold cannot trigger Stay away, so a 2 to 5 minute cadence suffices there and 30 seconds only matters late). The spoiler-free property is preserved trivially under polling, since the server still forwards only the verdict string to phones.

## 6. What is still unknown

* The exact `playId` join target for NFL and college football `winprobability` readings (which `drives` or `scoringPlays` entry each reading attaches to, and which clock field to use) was not verified; only the arrays' presence was confirmed.
* Whether NFL overtime or college overtime games report nonzero `tiePercentage` (all tested readings showed 0.0); a verdict rule for football should handle ties explicitly.
* ESPN's blocking threshold for sustained polling from one IP (burst tolerance was verified at 20 rapid requests, all HTTP 200; the long-run limit is unpublished).
* Whether NHL or soccer summaries ever carry win probability under different parameters (only default summary fetches were tested; alternate views such as `?event=` on other ESPN hosts were not).
* API-Sports pricing and win-probability coverage, and win-probability availability plus pricing for SportsDataIO, Sportradar, Stats Perform/Opta, and Genius Sports (all require sales contact or a JavaScript-capable browser session the script pass could not complete).
* Whether `cdn.nba.com` liveData play-by-play JSON carries any win-probability field (bot gating blocked all inspection).
